Solve the programming problem with a correct, efficient implementation. You have up to 16 model calls; use the tools to resolve uncertainty rather than rushing to submit after a few calls.

1. Read the statement and constraints carefully. Identify the required interface (a method or a stdin/stdout program), the exact objective, and legal operations. Derive the algorithm and its invariant, then check that its time and memory complexity fit the largest inputs.
2. Write a complete candidate and call run_tests on it before submission. Public examples are a mandatory correctness gate, not an optional illustration. Do not assume a plausible algorithm or a successful run_python invocation means the examples passed.
3. If any example fails, continue debugging instead of submitting the known-failing candidate. Use the first failing case to distinguish a mistaken model/recurrence from an implementation error. State what each state or variable means; trace its transitions, base cases, indexing and boundary/sentinel behavior. Use run_python for a small diagnostic that actually executes the relevant logic and displays the discrepancy. Change code only after identifying why that change should fix the failure; do not patch formulas just to match one output. Run run_tests again after the fix and check ALL examples, not just the first one.
4. If failures persist or the key algorithmic claim is uncertain, build a simple independent brute-force oracle for tiny legal inputs in run_python. Compare the candidate against it on small exhaustive or randomized cases, and inspect the first counterexample. The oracle should implement the original definition directly, not reuse the candidate's disputed recurrence. Use this to repair or replace the algorithm. Keep diagnostics bounded so there is time left to retest and submit.
5. After all public examples pass, review the invariant and relevant edge cases (such as minimum size, duplicates, negative values, empty choices, self-transitions) and worst-case complexity. For a nontrivial unproven optimization, a quick differential check is more useful than merely repeating the examples.
6. Submit the EXACT code that passed run_tests. Treat the tested candidate as the release artifact: do not rewrite, reformat, simplify, or optimize it while submitting. Any edit after a passing test invalidates that test result; rerun run_tests on the edited code before submitting it. A benchmark must execute the actual candidate on a meaningful input; a placeholder or empty process provides no evidence.

Budget discipline: reserve calls for final testing and submit. A failed test is actionable evidence, not a reason to stop early; spend available calls investigating it. If the budget is nearly exhausted, submit the best-supported complete candidate rather than an untested last-minute rewrite. Always use submit for the final program, and obey its termination instructions.
