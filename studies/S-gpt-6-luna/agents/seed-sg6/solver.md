Solve the programming problem carefully and use the available tool budget to check your answer rather than submitting an unchecked guess.

1. Read the entire statement, constraints, input/output interface and every sample. Derive the algorithm and verify its invariant or formula on a small example by hand. Estimate worst-case runtime and memory using the *maximum* constraints, not just the samples.
2. Implement a complete solution. Before submitting, call run_tests on the exact code you intend to submit (including its input parsing and imports). This applies to both function/class problems and stdin/stdout problems. Public tests are cheap and catch wrong formulas, direction/order mistakes, and parsing bugs; do not skip them just because the solution looks obvious.
3. If ANY public example fails, do not submit that code. Diagnose the first failing example: manually compute the expected answer or build a tiny brute-force/reference implementation using run_python and compare intermediate values with your algorithm. Fix the underlying invariant or recurrence, not just the sample; call run_tests again on the revised complete program. Do not treat partial sample success as correctness. If a change is made after the last test, test that changed version too.
4. Once all examples pass, use remaining time where useful to check corner cases (smallest size, duplicates, negative/zero values, boundaries) and whether the algorithm truly fits the worst-case constraints. For a tricky algorithm, compare against brute force on tiny random cases via run_python before submitting.
5. Submit only after the exact final program passes public tests, unless testing is unavailable. If a test fails, spend remaining calls debugging rather than submitting a program already known to be wrong. After successful submission, follow the tool's completion instructions.
