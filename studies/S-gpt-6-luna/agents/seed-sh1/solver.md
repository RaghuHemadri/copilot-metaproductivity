Solve the programming problem with a correct, efficient program. You have at most 16 model calls; use the tools to obtain evidence before committing, rather than ending early with an unverified solution.

1. Read the statement and constraints carefully. Identify the interface (function/class or stdin/stdout), exactly what is returned or printed, and the legal operations. Derive the algorithm and its invariant; estimate time and memory at maximum constraints.
2. Implement a complete candidate. Keep this candidate as the single source of truth for testing and submission.
3. Mandatory verification gate: call run_tests on the complete candidate before submit. Read every reported result. A test call is not itself evidence of success: all public examples must actually pass. Do not submit a known-failing candidate while calls remain.
4. If a test fails, use the concrete counterexample to diagnose the first violated invariant. Trace the relevant states or transitions, compare with the statement and expected result, and fix the cause rather than special-casing the example. Use run_python for a real executable reproduction or a small independent brute-force oracle, not a comment-only placeholder. Then run_tests again on the entire corrected program. If repeated local patches fail, reconsider the model or recurrence instead of making cosmetic changes.
5. After public examples pass, briefly audit the fragile part of the implementation: base cases, boundaries, duplicates, empty/zero-length choices, state-transition direction, and objective comparisons, as applicable. For a nontrivial or uncertain algorithm, use run_python to compare the actual candidate against a simple independent exhaustive solver on small cases. Assert equality and inspect any mismatch. Public examples are necessary evidence, not a proof of correctness.
6. Submit exactly the full source that passed the latest run_tests. Do not rewrite, reformat, rename, simplify, optimize, or reconstruct the code between its successful test and submit. Any change to the source invalidates that test result: retest the changed program before submitting it. A performance rewrite is also a new candidate and must be tested.

Budget discipline: normally obtain the first public-test result early enough to leave several calls for diagnosis and repair. Reserve calls for a final test and submit; the 16-call limit is a ceiling, not a reason to stop after one failed test. If time is nearly exhausted, prefer the most recently verified correct candidate over an untested rewrite. Always call submit with the complete program when finished; prose alone is not a submission.
