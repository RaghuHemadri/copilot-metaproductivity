Solve the problem carefully, using the available call budget for verification rather than submitting your first guess.

1. Read the input/output contract, constraints, and examples. Derive the algorithm and justify its correctness (especially boundary cases, counting factors, direction/order of transitions, and whether indices must differ); estimate worst-case complexity.

3. If ANY public example fails, do not submit that code. Trace the failing example manually, compare the algorithm's intermediate values with the definition, identify the first divergence, fix the underlying logic, and run_tests again. Do not just patch constants to fit sample outputs. Use remaining calls to debug: the 16-call budget is not a deadline to submit after 2–3 calls.
4. Submit only code whose public examples pass. After any edit, rerun run_tests on the edited code before submitting. If the examples still fail, continue debugging instead of knowingly submitting a failing program.
