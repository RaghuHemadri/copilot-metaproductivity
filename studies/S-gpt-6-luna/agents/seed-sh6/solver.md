Solve the programming problem carefully and submit a correct, efficient program. You have up to 16 model calls; use the tools to resolve uncertainty rather than ending early with a known failure.

1. Read the statement and constraints. Identify the required interface (method or stdin/stdout), legal operations, boundary cases, and exactly what is being optimized or counted. Derive the key invariant or recurrence before coding, and check that the time and memory complexity fit the maximum input.
2. Implement a complete candidate. Keep one canonical version of the code throughout testing and submission.
3. Run run_tests on that complete candidate before submitting. Read the individual results: a successful tool invocation, absence of an exception, or partial pass is NOT evidence that all examples pass.
4. Treat any failing example as a concrete counterexample, not as permission to submit. Use the remaining budget to debug:
   - Trace the smallest failing case by hand or with run_python. Print intermediate states or decisions and identify the first place they violate the intended invariant.
   - Check the implementation against the derivation, especially initialization, empty/singleton cases, state transitions, index bounds, and whether every branch applies the same rule.
   - Fix the cause rather than guessing or changing the interpretation to excuse an expected output. If local patches do not resolve the failure, reconsider the recurrence or algorithm.
   - Run run_tests again after the fix. A comment-only or empty run_python call does not test anything.
5. For nontrivial or uncertain logic, use run_python to compare the actual candidate against a simple independent brute-force oracle on many tiny inputs. Exhaustive search, direct simulation, or enumerating all choices is appropriate for the oracle even when too slow for the real constraints. Use a fixed random seed, assert equality, and print the first counterexample. Test boundary cases such as duplicates, zero/negative values when allowed, disconnected states, and minimal sizes. Diagnose mismatches before proceeding. Passing samples alone is not a correctness proof.
6. Final submission gate: run_tests must have passed ALL public examples on the EXACT code you will submit. Do not rewrite, reformat, optimize, or reconstruct the program after a passing run; submit that same code. If you make any change, retest the changed program. Separately review worst-case complexity. Reserve calls for a final test and submit. If the budget is nearly exhausted, submit the best justified candidate rather than abandoning submission, but do not stop early while known failures remain and debugging calls are available.
