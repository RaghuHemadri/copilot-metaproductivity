Solve the programming problem carefully and submit a complete program in the required interface.

1. Read the statement and constraints. Identify the input/output contract, derive the algorithm and its invariant, and check that its time and memory complexity fit.
2. Implement the algorithm. Keep one canonical candidate program: the code you test is the code you will submit.
3. Verification is a required stage, not an optional formality. Call run_tests on the complete candidate before submit, even if the solution seems obvious. You have up to 16 model calls; do not rush to submit in two or three calls while correctness is unresolved. Reserve calls for debugging and final verification.
4. If a public example fails, do not submit or merely reformat the code. Inspect the actual and expected results, trace the smallest failing case, and identify the violated invariant, incorrect formula, missing condition, or implementation bug. Revisit the derivation if necessary. Fix the cause and run_tests again. A changed candidate has not passed until that changed candidate is tested.
5. Before finalizing, inspect boundary cases and state transitions relevant to this algorithm (for example empty/singleton states, duplicate values versus distinct indices, initialization overlaps, direction/index conventions, and bounds of precomputed tables). When the derivation is uncertain, use run_python to compare the actual candidate against a simple independent brute-force oracle on many small cases; inspect the first mismatch rather than patching blindly. This supplements, not replaces, public tests.
6. Submit the EXACT complete program from the successful final run_tests call. Do not rewrite, clean up, optimize, or reconstruct it between testing and submission. If any code changes, run_tests again on the new complete program. A successful test of an earlier version does not certify the submitted version.

For problems allowing multiple valid outputs, a textual sample mismatch may be legitimate: check the candidate output against every stated validity condition with an independent checker before treating it as acceptable. Do not hardcode sample outputs. For deterministic outputs, a remaining sample mismatch is an unresolved bug, not a reason to stop debugging. If nearing the call limit, prioritize fixing and retesting the existing candidate over cosmetic rewrites; still submit your best complete solution before the budget is exhausted.
