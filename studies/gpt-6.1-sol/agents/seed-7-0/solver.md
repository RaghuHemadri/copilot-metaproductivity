Solve the problem step by step:
1. Read the statement and the constraints carefully. Identify the input format and exactly what must be printed.
2. Choose an algorithm whose time complexity fits the constraints.
3. Write a complete program and check it with run_tests.
4. If an example fails, find the bug, fix it and run the tests again.
5. Independently audit correctness before submission; sample success and a speed benchmark are not a correctness proof. For a nontrivial algorithm, use run_python for a bounded small-instance differential test against a simple brute-force/reference implementation, or an independent validator when outputs are non-unique. Generate only inputs satisfying the statement's constraints. Test boundary cases and several tiny exhaustive or randomized cases, especially the assumptions on which the algorithm depends (strict versus non-strict inequalities, ties, empty/disconnected cases, indexing, and degenerate structures). Exercise the actual candidate logic, not just a simplified reimplementation. For optimization compare objective values with the reference; for constructions verify every required condition, range, and output dimension rather than equality with one reference output. Keep tests small enough to finish quickly and use any counterexample to fix the algorithm, then rerun tests.
   Interpret test feedback against the specification: if a construction differs from a sample, independently validate both feasibility and any required optimality before deciding it is a bug. A literal-output mismatch alone does not disprove a valid non-unique answer. Do not memorize sample outputs, invent unsupported tie-breaking requirements, or weaken explicit input/output constraints to match a suspect checker. If examples fail because of a genuine violation, fix it before proceeding. Reserve calls for correction and submission; the 16-call budget usually permits both correctness and performance checks.
6. Before submission, audit performance at the maximum constraints. Passing small examples is not evidence of adequate speed. Count the total work of the actual implementation, including nested scans, slicing/copying, allocation, and repeated preprocessing. An amortized bound for one invocation must be summed over all invocations. In Python, quadratic algorithms with millions of inner-loop iterations can be borderline even when their asymptotic complexity is appropriate.
   If performance is plausibly tight, use run_python to benchmark the candidate on a generated maximum-size input, not just a small random input. Choose patterns that maximize work (such as all-equal, short-period, monotone, or dense inputs, as appropriate); early exits on random data can conceal the worst case. Generate inputs programmatically and time the actual core algorithm without printing huge outputs. Keep the experiment bounded; a clearly slow smaller run already warrants improvement. Use the available call budget to revise and remeasure rather than submitting a known slow implementation. Prefer reducing total work or using efficient built-in operations over cosmetic changes. Leave a comfortable time margin and check memory as well.
7. When correctness and performance are justified, submit the program.
