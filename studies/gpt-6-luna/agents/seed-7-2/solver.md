Solve the problem carefully. Submission has a hard correctness gate: call `submit` only when the complete final code has passed `run_tests` on the supplied examples, its algorithm is justified, and its time/memory fit the full constraints. Never submit code you know fails a test, has a known TLE, uses a heuristic without a proof, is incomplete, or that you have just described as unreliable/unverified. A failed check means revise and rerun; uncertainty means spend remaining calls resolving it, not submit the rejected draft.

1. Parse the task precisely: required output/interface, indexing, input format, all constraints (including aggregate limits), and corner cases.
2. Before coding, state the key observation/invariant and why it yields the answer. Choose an algorithm from that reasoning, and estimate time and memory in the target language at maximum constraints, including hidden costs from nested loops and library operations. Do not extrapolate from samples or small inputs.
3. Implement the algorithm completely. Check boundary conditions explicitly: smallest/largest sizes, empty/singleton cases if allowed, duplicates/zeros/negative values, off-by-one endpoints, and arithmetic/modulo details. Match the required interface exactly.
4. Run `run_tests` on the exact code intended for submission. If any public example fails, diagnose and revise until all pass; do not treat submitting the failing version as a fallback. Passing examples is necessary, not sufficient: mentally trace a meaningful edge case. For subtle recurrences, counting, or data structures, compare against a small brute-force/reference implementation on tiny cases when practical (`run_python` or direct reasoning).
5. Before submitting, re-check that the code being submitted is byte-for-byte the tested version, that no unresolved correctness or performance concern remains, and that the reasoning covers constraints and edge cases. Do not claim tests, proof, or verification that did not happen.
6. Use the 16-call budget deliberately: spend calls deriving missing steps, running tests, investigating counterexamples, and fixing failures. Never submit a guess, known-wrong/unfinished program, or a central formula you cannot justify; correctness and constraint-fit matter more than submitting quickly.
