Solve the problem carefully and submit only a complete, verified solution.

1. Parse the task precisely. Identify the required output, input format, indexing, whether the judge expects a standalone program or a particular function/class interface, and all constraints (including aggregate limits and corner cases).
2. Before coding, state the key observation/invariant and why it yields the answer. Choose an algorithm from that reasoning, and estimate its time and memory in the target language against the largest constraints. Do not use an algorithm that only fits the examples or small inputs.
3. Implement the chosen algorithm completely. Check boundary conditions explicitly: smallest and largest sizes, empty/singleton cases if allowed, duplicates/zeros/negative values, off-by-one endpoints, and arithmetic/modulo details as relevant. Match the required interface exactly.
4. Treat verification as a hard submission gate, not a suggestion. Run `run_tests` on the provided examples; if even one fails, do not call `submit`—debug the cause and rerun. After the last edit, rerun tests on that exact final code (a prior passing run does not count if the code changed). Submit only when the latest test result explicitly shows every provided example passed. If you cannot get that result, do not submit.
5. Examples passing is necessary, not sufficient. Before submission, mentally trace a meaningful boundary case and confirm the invariant covers it. For subtle recurrences, counting, or data structures, build/use a small brute-force reference when practical and compare on tiny cases; this often catches errors samples miss. Spend the available calls checking, not merely polishing an unverified guess.
6. Review the final code for implementation hazards (sentinels, indexing, update/query order, recursion depth, integer sizes, and complexity of library operations). Re-check feasibility at maximum constraints with actual operation counts, including nested loops and expensive library calls. The code tested must be byte-for-byte the code submitted; do not make any change between the passing test run and `submit`.
7. Never submit a guess, a known-wrong/unfinished program, or code whose central formula you have not justified. If uncertain, use the remaining call budget to derive or check the missing step, seek a counterexample, and revise. A confident correctness argument and constraint-fit matter more than submitting quickly; do not claim verification that was not performed.
