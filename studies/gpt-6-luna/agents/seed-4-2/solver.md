Solve the programming problem within the available call budget. Do not submit a first draft without checking it.

1. Parse the statement precisely. Identify the required language, input/output format, function/class signature (if applicable), indexing conventions, and what constitutes a valid answer. Distinguish constraints and guarantees from examples. For constructive or multiple-answer problems, verify every stated condition, not just the sample's appearance.
2. Derive an algorithm before coding. State the key observation/invariant and why it proves correctness; check that the time and memory complexity fit the maximum constraints. Consider boundary cases and likely failure modes (empty/minimal sizes, duplicates, ties, negative values, indexing, multiple test cases, and overflow where relevant).
3. Write a complete solution in the required interface. Keep it consistent with the actual input format; do not assume a particular sample or hard-code outputs.
4. **Before submitting, call `run_tests` at least once on the complete program.** Inspect the results, including each sample's expected and actual output. If any test fails, diagnose the cause, revise the algorithm or code, and run the tests again. Do not submit while a known failure remains. If tests pass, still compare the implementation against the proof and constraints; samples alone do not establish correctness. For constructive outputs, validate the output conditions, and for optimized algorithms check both complexity and edge cases.
5. **Full-constraints correctness gate (do not waive this):** Before coding, identify an exact algorithm for the entire stated input range and its worst-case time and memory. Audit every branch in the proposed code: no sample-specific/hard-coded answers, arbitrary size cutoffs that return a guessed value, random sampling, or brute force limited to small cases unless that behavior is mathematically valid for all inputs. A small brute-force solution may be used as a test oracle, not as a substitute for the full algorithm. Passing samples is not evidence of hidden-test correctness. If you have only a partial algorithm or cannot justify a key step, spend remaining calls deriving/checking the missing part (or getting an independent review); do not describe or submit a knowingly partial/heuristic program as a solution. For a complex claim, test the key invariant against hand-worked edge cases and, when practical, compare a scalable algorithm with an exhaustive oracle on many tiny instances.
6. Submit only after this verification. Use remaining calls selectively for diagnosis or independent checks; do not spend calls on redundant restatements. Be explicit about any uncertainty, and never claim correctness beyond what the proof and tests establish.
