## Hard submission gate
Do not call `submit` merely because a program exists or the call budget is low. Before submission, the exact final code must pass `run_tests` on every provided example, and you must be able to justify that its algorithm is correct and fits the full constraints. If any example fails (including timeout or runtime error), the current code is not eligible for submission: revise it and rerun all examples. If the last test run is not fully passing, do not call `submit`; stop and state that you could not complete a verified solution. If the proposed code is a placeholder, handles only small cases, prints a default answer for unsupported cases, is knowingly too slow, or you have just concluded that you cannot derive/verify the required algorithm, do not submit it. Never contradict an uncertainty statement by submitting that same unverified code. Use remaining calls to derive, test, or debug; submit only after clearing this gate.

1. Parse the task precisely. Identify the required output, input format, indexing, whether the judge expects a standalone program or a particular function/class interface, and all constraints (including aggregate limits and corner cases).
2. Before coding, state the key observation/invariant and why it yields the answer. Choose an algorithm from that reasoning, and estimate its time and memory in the target language against the largest constraints. Do not use an algorithm that only fits the examples or small inputs.
3. Implement the chosen algorithm completely. Check boundary conditions explicitly: smallest and largest sizes, empty/singleton cases if allowed, duplicates/zeros/negative values, off-by-one endpoints, and arithmetic/modulo details as relevant. Match the required interface exactly.
4. Verify the exact code with `run_tests` on the provided examples before submission. If any example fails, debug and rerun; do not submit code that has not passed them. Passing examples is necessary, not sufficient: mentally trace at least one meaningful edge case and check that the invariant covers it. If a small brute-force/reference solution is practical, compare it with the optimized algorithm on tiny cases (using `run_python` or direct reasoning); prioritize this for subtle recurrences, counting, and data structures.
5. Review the final code for implementation hazards (sentinels, indexing, update/query order, recursion depth, integer sizes, and complexity of library operations). Make sure the tested code is exactly the code being submitted.
6. Never submit a guess, a known-wrong/unfinished program, or code whose central formula you have not justified. If uncertain, use the remaining call budget to derive or check the missing step, seek a counterexample, and revise. A confident correctness argument and constraint-fit matter more than submitting quickly; do not claim verification that was not performed.
