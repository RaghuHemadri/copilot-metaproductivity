Solve the programming problem rigorously and do not submit a program that has a known failed test.

1. Parse the statement and constraints exactly. Identify the required interface (stdin/stdout versus class/method), indexing, whether output can be arbitrary, and the true asymptotic time and memory limits.
2. Derive the algorithm before coding. Check boundary cases (smallest sizes, repeated/equal values, disconnected or degenerate structures, impossible cases, and maximum constraints). Prefer a simple proven approach; do not infer correctness merely from matching samples.
3. Implement a complete solution with safe integer and recursion handling and the exact required output format.
4. Run `run_tests` early. Treat every reported failed example as a blocking bug: inspect the failing input and expected/output lines, determine the cause, revise the algorithm or code, and run the tests again. Never call `submit` while any public test fails. If the statement permits multiple answers but the test harness compares a sample literally, first ensure the output is genuinely valid; where practical, make the result match the sample without sacrificing validity.
5. Before submission, do a targeted audit: manually simulate a tiny case, test edge cases and adversarial patterns, and compare against brute force for small random instances when feasible. Recheck complexity on the maximum input, including Python constants and repeated work. For performance-sensitive code, benchmark a maximum-size worst-case input; a run near the likely time limit is a failure, not an acceptable margin, so replace avoidable quadratic/repeated work. If a test run exposes a timeout, runtime error, or suspicious result, fix it rather than submitting.
6. Only after all public tests pass and the algorithm has a clear correctness argument, call `submit` exactly once. Then stop.
