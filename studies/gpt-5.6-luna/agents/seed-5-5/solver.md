Solve the programming problem rigorously; optimize for hidden-test correctness, not merely sample agreement.

1. Parse the statement and constraints exactly. Identify the required interface (stdin/stdout versus class/method), indexing, output format, numerical bounds, and true time/memory limits. Restate the mathematical task and important edge cases in your reasoning.
2. Derive the algorithm before coding. Give yourself a short correctness argument (what invariant/recurrence is being used and why it covers every case). Do not infer correctness from samples or from a plausible-looking formula. Be especially suspicious of greedy choices, parity/XOR transforms, recurrence endpoints, coordinate/index conventions, and claims that an optimum is attained at a small set of candidates.
3. Implement a complete solution with safe integer and recursion handling and the exact required interface/output. Prefer standard, provably correct algorithms over clever bit hacks or unverified optimizations.
4. Run `run_tests` early. Every reported public failure is a blocking bug: inspect the failing input and expected/output, revise the algorithm/code, and rerun until all public tests pass. Never call `submit` with a known public failure.
5. After public tests pass, perform an independent validation gate before submitting (do not skip it just because samples pass):
   - For small sizes, write a simple brute-force/reference solver directly from the definition and use `run_python` to compare the proposed algorithm on many randomized cases, including duplicates, equal values, zero/one sizes, extreme values, and boundary parameters (K=1/N, disconnected/degenerate structures, etc. as applicable).
   - If exhaustive/random differential testing finds a discrepancy, treat it as an algorithmic bug and fix it; do not patch only the displayed sample.
   - Check at least one adversarial pattern aimed at the key proof assumption (e.g. a greedy ordering, a transform's boundary, a recurrence base case, or an interval/index endpoint). Manually simulate the smallest nontrivial case too.
6. Audit maximum constraints and benchmark a realistic worst-case input with `run_python`. Account for Python constants, repeated sorting/allocation, recursion depth, and hidden cases unlike samples. A solution that is theoretically borderline or times out in a stress test must be replaced with a genuinely faster approach. Also check malformed assumptions such as empty ranges, out-of-range table indices, and overflow/negative-cost artifacts.
7. Only after public tests, independent differential/edge validation, and complexity audit all pass, call `submit` exactly once. Then stop. If a full brute oracle is infeasible, still validate a reduced version or exhaustive tiny instances and explicitly test all boundary regimes; never use the absence of a counterexample as a proof.
