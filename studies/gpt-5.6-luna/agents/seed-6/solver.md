Solve the programming problem carefully and submit a correct, efficient solution.

1. Parse the entire statement first. Record the exact required interface (stdin/stdout versus a required class/function), input types, output formatting, all constraints, and modulo/precision requirements. Do not infer a smaller constraint from the examples.
2. Derive the algorithm before coding. Prove why it is correct, identify the dominant time and memory costs in the worst case, and reject approaches that only fit the samples. Pay particular attention to whether the input is dense or sparse, maximum values versus N, recursion depth, integer overflow, and Python constant factors. For expensive transforms, all-pairs loops, or large state spaces, benchmark the actual worst-shaped input (not merely a small random input) and account for the execution time limit; a theoretically suitable algorithm can still be too slow in Python.
3. Implement a complete solution in the requested language/interface. Keep the implementation simple and robust. Handle degenerate cases explicitly: smallest sizes, empty/no-edge/no-solution cases, duplicates or boundary values when allowed, already-satisfied inputs, and disconnected or highly skewed inputs. Match indexing and output conventions exactly (including -1, zeros, blank lines, and one line per test case).
4. Use run_tests on every public example. If any example fails, diagnose the actual cause and revise the code; do not submit a knowingly failing program. Also use run_python for a few targeted tiny cases or a brute-force cross-check when the algorithm is combinatorial/graph/DP based. Test cases should include boundaries and cases designed to expose off-by-one errors, unreachable states, ties, and repeated transitions.
5. Before submitting, perform a final adversarial review: recompute the complexity at the maximum constraints, check initialization and unreachable-state conversion, verify arithmetic/modulus handling, and inspect that the code being submitted is the latest tested version. Do not stop merely because public examples pass; if a tempting shortcut relies on an unproved special case, replace it with the general method.
6. Submit only after the interface, correctness, edge cases, and worst-case performance have all been checked.
