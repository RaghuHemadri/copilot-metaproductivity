Solve the programming problem rigorously. Do not submit a program that is known to fail, and do not submit merely because you ran out of ideas.

NON-NEGOTIABLE SUBMISSION GATE: `submit` is irreversible. A `run_tests` result such as 0/3 or 2/3 means STOP DEBUGGING, not submit. The only permitted reason to call `submit` is a latest full `run_tests` result with every example passed; a timeout, runtime error, or wrong answer on even one example fails this gate.

WORKFLOW (the submission gate is absolute):
1. Parse the statement and constraints exactly. Identify the required interface (stdin/stdout versus class/method), indexing, output format, and the true asymptotic time and memory limits.
2. Derive the algorithm before coding. State the key invariant/correctness argument mentally or in notes, and check boundary cases (smallest sizes, repeated/equal values, disconnected or degenerate structures, impossible cases, and maximum constraints). Prefer a simple proven approach; do not infer correctness merely from matching samples.
3. Implement a complete solution with safe integer and recursion handling and the exact required output format.
4. Run `run_tests` as soon as there is a candidate. Every failed public example is a blocking defect. Inspect the actual failing input and expected/output lines, find the cause, revise the algorithm or code, and rerun. After each revision, rerun the full public suite rather than relying on one fixed example. NEVER call `submit` if the most recent full `run_tests` result is not 100% passed; this rule still applies when the failure seems like a harness quirk or when the model-call budget is getting low.
5. Before submission, perform a targeted correctness audit, not just a sample check. Manually simulate tiny cases and edge cases. For nontrivial algorithms, write a tiny brute-force/reference solver in a `run_python` call and compare the candidate against it on many random small instances (or exhaustively enumerate small instances) whenever feasible. Use any mismatch to repair the derivation, not to justify submitting. For multiple-answer outputs, check validity rather than literal sample equality.
6. Audit complexity on the maximum constraints, including Python constants, memory, recursion depth, and repeated work. For performance-sensitive code, benchmark a worst-case-shaped input; a run near the likely limit is a failure, so replace avoidable quadratic work. Treat timeout, runtime error, suspicious output, or failed differential testing as blocking defects.
7. Only when (a) the latest complete public suite is entirely green, (b) the algorithm has a clear correctness argument, and (c) the complexity/edge-case audit has no unresolved concern, call `submit` exactly once. Then stop. If these conditions cannot be met, keep debugging or do not submit; never knowingly submit a failing program.
