Solve the programming problem rigorously and do not submit a program that has a known failed test.

1. Parse the statement and constraints exactly. Identify the required interface (stdin/stdout versus class/method), indexing, output types/format (including booleans), whether output can be arbitrary, and the true asymptotic time and memory limits.
2. Derive the algorithm before coding. Check boundary cases (smallest sizes, repeated/equal values, disconnected or degenerate structures, impossible cases, and maximum constraints). Prefer a simple proven approach; do not infer correctness merely from matching samples. For a nontrivial formula/greedy/transform, state why it is correct and test it against a brute-force model on tiny random cases when feasible.
3. Implement a complete solution with safe integer and recursion handling and the exact required output format.
4. Run `run_tests` early. Treat every reported failed example as a blocking bug: inspect the failing input and expected/output lines, determine the cause, revise the algorithm or code, and run the tests again. Never call `submit` while any public test fails. This is a hard submission gate, not a suggestion: if the latest `run_tests` result is not 100%, do not submit under any circumstances; spend the remaining calls fixing it or leave unsent. Do not let a plausible proof or a timeout of an exploratory test override a failing public test.
5. Before submission, do a targeted audit: manually simulate a tiny case, test edge cases and adversarial patterns, and compare against brute force for small random instances when feasible. Recheck complexity on the maximum input, including Python constants and repeated work. For performance-sensitive code, benchmark a maximum-size worst-case input; a run near the likely time limit is a failure, not an acceptable margin, so replace avoidable quadratic/repeated work. For combinatorial counting or algebraic transforms, separately check empty/zero terms, parity/index ranges, modular inverses, and coefficient-array bounds. For greedy choices, try an exchange/counterexample test rather than relying on samples. If a test run exposes a timeout, runtime error, or suspicious result, fix it rather than submitting.
6. Only after all public tests pass and the algorithm has a clear correctness argument, call `submit` exactly once. Then stop. Never submit merely because the model-call budget remains or because samples passed earlier; the most recent code must be the code tested and submitted.
