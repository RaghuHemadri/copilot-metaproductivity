Solve the programming problem rigorously. Your goal is a correct, efficient submission, not merely a program that matches the samples.

1. Parse the statement and constraints exactly. Identify the required interface (stdin/stdout versus class/method), indexing, output format, whether answers are unique, and the true asymptotic time and memory limits. Write down the invariant or mathematical quantity being computed.
2. Derive the algorithm before coding. State why it is correct, and check boundary cases (smallest sizes, repeated/equal values, disconnected or degenerate structures, impossible cases, and maximum constraints). Do not infer correctness from examples or from an appealing formula. Be especially suspicious of greedy choices, endpoint assumptions, parity, off-by-one ranges, modular arithmetic, and transformations that silently change the problem.
3. Implement a complete solution with safe integer and recursion handling and the exact required interface/output. Keep the implementation consistent with the derived proof; do not leave a provisional heuristic in the submitted code.
4. Run `run_tests` early. Every reported failed public example is a blocking bug: inspect the exact input and expected/output, revise the algorithm or code, and rerun. Never call `submit` after a failed test run. The submission gate is strict: the most recent run of the current exact code must report all public examples passed (not merely that an earlier version passed).
5. Before submission, spend at least one verification pass beyond the samples. For small domains, write a brute-force/reference solver and use `run_python` or randomized differential tests against it; otherwise construct adversarial tests from each boundary and from the proof's assumptions. Test cases with duplicates, all equal values, zeros, extreme values, minimum/maximum sizes, and structures that maximize transitions or collisions. If a proposed optimization has a delicate index or recurrence, directly compare it to the obvious definition on many tiny random cases. A passing sample suite is not evidence that hidden cases pass.
6. Audit complexity on the maximum input, including Python constants, memory, recursion depth, repeated sorting/allocation, and worst-case rather than average-case behavior. For performance-sensitive code, benchmark a realistic worst-case input. A run near the likely time limit is a failure: replace avoidable quadratic work, huge integers, repeated transforms, or per-query rebuilding. Also check that all intermediate array indices are valid for minimum and maximum parameter values.
7. If any test, randomized check, benchmark, or reasoning exposes a timeout, runtime error, mismatch, or suspicious assumption, that is a blocking failure exactly like a failed public example: immediately revise the solution, rerun the check, and keep iterating. Never stop with a known counterexample, even if it came from your own brute-force script; do not rationalize it or submit merely because the budget remains small. Only after the current code passes public tests, has a clear correctness argument, and survives targeted verification, call `submit` exactly once; then stop.
